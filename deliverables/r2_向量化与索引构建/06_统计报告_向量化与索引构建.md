## 0 符号与参数词典

读之前先对齐符号。每个字母的形状决定了它后面能怎么运算。

| 符号 | 英文 | 中文 | 形状 / 直觉 |
|---|---|---|---|
| $q$ | query vector 查询向量 | 查询向量 | 1 个 1024 维行向量，由用户的问题编码而来 |
| $d$ | document vector 文档向量 | 块向量 | 1 个 1024 维行向量，由 1 个文本块编码而来 |
| $N$ | number of chunks | 块总数 | 标量，本项目 $N = 27\,349$ |
| $B$ | batch size | 批大小 | 标量，一次送进模型多少个块 |
| $r$ | throughput | 吞吐 | 块/秒，实测决定，不是理论值 |
| $T$ | total time | 总耗时 | 标量，$T = N / r$ |
| $D$ | dimension | 向量维度 | bge-m3 为 1024 |
| $\|x\|$ | L2 norm | 向量模长 | 标量，向量到原点的距离：$\|x\|=\sqrt{\sum_i x_i^2}$ |
| $\cos(q,d)$ | cosine similarity | 余弦相似度 | $[-1,1]$，**只看方向不看长度** |
| $\delta$ | distance | 距离 | Chroma 返回值，$\delta = 1 - \cos$ |

关键直觉：**向量 = 一个点在高维空间里的位置；相似度 = 两个方向的夹角。** 模长是"音量"，夹角是"语义"。RAG 关心语义，所以要消掉音量。

## 1 先探硬件，再谈选型

模型选型不是"挑排行榜最高的"，而是**在约束下找唯一可行解**。所以第一步不是比较模型，是摸清机器。

| 项 | 实测值 | 对选型的约束 |
|---|---|---|
| GPU | 无（`torch.cuda.is_available() = False`） | 任务书里"8 GB / 16 GB"标注均为 GPU 显存，落到 CPU 上推理要慢 10–50 倍 |
| CPU | 8 线程 | 吞吐上限由它决定，与 batch 大小无关 |
| 内存 | 27.8 GB（可用 10.6 GB） | 足够，不是瓶颈 |
| 本地推理栈 | Ollama 0.34，bge-m3 已拉取（1.2 GB） | 已有 GGUF 量化版，零安装成本 |

这条约束链直接否掉了"越大越好"的思路：**在无 GPU 的机器上，模型每大一号，全量耗时就翻一倍以上**，而 27 349 块 × 1024 维这个规模，耗时的单位是"小时"不是"分钟"。

## 2 嵌入模型选型：排除链

任务书给了 4 个候选。结论不是"bge-m3 最好"，而是**前三个都有硬阻塞**。

| 候选 | 结论 | 依据（阻塞点） |
|---|---|---|
| `BAAI/bge-small-en-v1.5`<br>`bge-base-en-v1.5`<br>`bge-large-en-v1.5` | 排除 | 后缀 `en` = 纯英文训练。语料 997 en + 9 zh（阶段③报告 §2），中文块会被编码成噪声向量，检索时永远召不回。此外 large 标注 16 GB，本机 CPU 推理无法承受 |
| `text-embedding-3-small`<br>`text-embedding-3-large` | 排除 | 付费 + 联网；27 349 块要走 API 限流与重试。**更关键的是离线不可复现**——交付物要求可查证，依赖付费 API 的实验第三方跑不了 |
| clinicalBERT | 排除 | 任务书自注"需自行微调"。微调需要 (query, 相关文档) 标注对，我们只有文献正文，**没有相关性标注**，做不了 |
| **`bge-m3`** | **采纳** | 1024 维、8192 token 输入上限、100+ 语言；Ollama 已有 GGUF 版可直接调用；与阶段③切块用的 tokenizer 同源 |

选型的正确记录方式：写**排除链**，不写结果。写结果别人无法判断换环境后还成不成立；写排除链，换个机器只要重新检查这几条阻塞点还在不在即可。

## 3 吞吐基准：为什么不选完就开跑

全量 27 349 块，跑起来才发现慢就废了几小时。所以先用 256 块样本扫 batch，再决定参数。

### 3.1 耗时公式

$$
T = \frac{N}{r}
$$

其中 $r$（块/秒）**只能实测，不能估算**——它取决于模型大小、量化方式、CPU 核数、文本平均长度，任何一项变了结论就变。

### 3.2 batch 扫描实测

| $B$ | 实测 $r$ | 全量外推 $T$ | 备注 |
|---|---|---|---|
| 1（逐块） | 0.44 块/s | 1036 min | 慢 4 倍 |
| 32 | 1.65 块/s | 276 min | 已接近饱和 |
| **64** | **1.70 块/s** | **268 min** | **选用** |
| 256 | 1.85 块/s | 246 min | 仅再快 9% |

**为什么批量能快 4 倍**：每次调用有固定开销（HTTP + 调度 + tokenize），批内被摊薄；同时大矩阵乘能让 BLAS 吃满 8 线程。

**为什么停在 64 而不上 256**：32 之后吞吐就饱和了——瓶颈是 CPU 算力，不是调度开销。再加大 $B$ 只带来两个坏处：内存峰值上升、单次失败要重算的块变多。**收益 9%，风险变高，不划算。**

### 3.3 全量实际耗时（含一次故障，见 §7）

| 阶段 | 时间区间 | 速率 | 说明 |
|---|---|---|---|
| 首段 0 → 12 480 | 16:51 – 18:12 | ~1.9 块/s | 稳定 |
| **卡死** | 18:12 – 20:33 | — | `ReadTimeout` ×2 + `502`，空耗约 2 h |
| 续跑 14 080 → 27 349 | 20:39 – 00:08 | 1.06 块/s | 含一次 502 重试，脚本计时 209.5 min |

总墙钟约 7.3 h，其中有效计算约 5.4 h。

## 4 查询向量与"指令前缀"：任务书结论在这里不成立

任务书写"BGE 查询添加指令获得更好的检索效果"。该结论**来自 bge v1.5 系列**官方建议（加前缀 `Represent this sentence for searching relevant passages: `）。bge-m3 训练时已内化检索指令，官方说明查询端**不需要**前缀。

两者矛盾，所以做了对照实验，不靠文档背书：

| 配置 | top1 | sim | 人工判断 |
|---|---|---|---|
| 无指令 | `PMC11219383_0001` | **0.7422** | 孟德尔随机化研究：二甲双胍与血压/心血管结局 —— 切题 |
| 加指令 | `PMC10133371_0021` | 0.6833 | top1 被换掉，整体相似度下降 |

**决策：默认关闭 `--instruction`**，开关保留在 CLI 与 `MedicalIndex(instruction=)` 上。将来若换成 `bge-base-en-v1.5`，此结论作废，需重测。

方法论：**文档结论有适用边界，跨模型必须重测。** 这条比"加不加前缀"这个具体答案重要得多。

### 4.1 查询与文档必须用同一个模型

`MedicalIndex.query()` 的 `embedding_model` 参数必须与建库时一致。原因：不同模型的向量空间不同，$q$ 与 $d$ 不在同一个空间里做点积没有意义——数值能算出来，但语义无效。

## 5 ChromaDB 索引设计

### 5.1 为什么要分两步（嵌入 / 索引分离）

| 步骤 | 耗时 | 性质 |
|---|---|---|
| 嵌入 → `embeddings_bge-m3.npy` | 209.5 min | **昂贵、一次性资产** |
| 灌库 → ChromaDB | 2.1 min | **便宜、参数可调** |

差 100 倍。所以嵌入落 npy 中间产物，索引独立成步：以后改 collection 名、元数据字段、距离度量，用 `--skip-embed` 两分钟重建即可，绝不重算向量。

### 5.2 为什么用余弦相似度

**问题**：要用一个数衡量"两个文本块语义有多近"。
**需求清单**：① 与训练目标一致；② 不受文本长度影响；③ 有界、可比较。

嵌入模型的训练目标就是让语义相关的文本向量**方向接近**。余弦相似度正好只保留方向：

$$
\cos(q,d)=\frac{q\cdot d}{\|q\|\,\|d\|}=\frac{\sum_{i=1}^{D} q_i d_i}{\sqrt{\sum_{i=1}^{D} q_i^2}\,\sqrt{\sum_{i=1}^{D} d_i^2}}
$$

分母把两个向量各自归一化到单位长度，于是结果与模长无关。

**为什么不用 L2（欧氏距离）**：模长会被文本长度和词频重复放大，而这两者不代表语义差异。一篇把同一个词重复 50 次的块，模长很大，但语义没变。

**为什么不用内积（ip）**：由点积定义

$$
q\cdot d=\cos(q,d)\,\|q\|\,\|d\|
$$

内积 = 余弦 × 两个模长，同样受模长干扰。只有当模型**专门以内积为目标训练**时才该用 ip —— bge 系列不是。

**Chroma 的返回值换算**：`hnsw:space="cosine"` 下 Chroma 返回 $\delta = 1 - \cos$，所以

$$
\text{sim} = 1 - \delta = \cos(q,d)
$$

### 5.3 id 设计：`doc_id + chunk_index`

格式 `PMC10010752_0000`。

- **唯一性推导**：`doc_id` 在库内唯一（一篇文献一个 ID）⊕ `chunk_index` 在篇内唯一（0..total_chunks-1）⟹ 拼接必然全局唯一。
- **幂等性**：Chroma 不指定 id 时会生成随机 UUID，重复 `add` 会堆出重复条目、污染 `count()`。显式 id 让"重跑 = 覆盖"，无需先清空。

### 5.4 元数据字段

| 字段 | 用途分类 | 作用 |
|---|---|---|
| `lang` `pub_year` `is_table` | 过滤 | 检索时缩小范围（见 §6.4） |
| `pmid` `doi` `journal` `source_title` | 溯源 | r3 生成答案必须给出处，否则医学场景不可用 |
| `doc_id` `chunk_index` `total_chunks` | 结构 | 定位与重组上下文 |
| `token_count` `tail_cut` | 质量 | 追溯切块阶段的遗留问题（阶段③报告 §5-6） |

`clean_meta()` 存在的唯一原因：ChromaDB 拒绝 `None` / `NaN`，需统一转空串，bool 保持原样。

**存储量计算**（为什么用 memmap 也够用）：

$$
27\,349 \times 1024 \times 4\ \text{bytes} = 111.9\ \text{MB}
$$

## 6 质量验证（`scripts/verify_index.py`）

**核心观点：`count()` 对了不等于库对了。** 库可能有三类错，必须用三类测试分别抓。

| 错误类型 | 检测手段 | 实测结果 |
|---|---|---|
| 数量错（漏批 / 重复） | `count()` 与块数对比 | 27 349 = 27 349 **PASS** |
| 绑定错（id↔向量↔文本错位） | 自相似性（§6.2） | exact 8/8，跨篇 0/8 **PASS** |
| 语义错（检索不相关） | 人工探针查询 | top1 sim 0.742 切题 **PASS** |
| 过滤失效 | 验证返回值满足条件（§6.4） | 4 种全 **PASS** |
| 边界崩溃 | 空 / 超长 / 乱码 | 均不报错 |

### 6.1 基础统计

```
collection      medical_chunks   metadata={'hnsw:space': 'cosine'}
向量总数        27349
样本0  id=PMC10010752_0000

```

与 `index_stats.json` 一致：27 349 条 / 1024 维 / bge-m3 / 1006 篇 / 块长 mean 383.5、max 509、min 32。

### 6.2 自相似性——为什么它是最强的一个测试

**做法**：从库里取一段原文当查询，看 top1 是不是它自己。

**为什么这一个测试能验证绑定**：如果 `emb` 的行序与 `df` 的行序错位（哪怕只错一行），top1 就会返回**别的文档**的块。它同时验证了 id、向量、文本、元数据四者对齐——别的测试都做不到。

**踩过的坑（指标设计案例）**：

| 查询文本长度 | 结果 |
|---|---|
| 截断到 300 字符 | 5/8，3 个 MISS 全是**同篇相邻块**（`PMC8500622_0001 → _0000`） |
| 截断到 1200 字符 | **8/8**，平均自相似 **0.9690** |

原因：切块有 64 token overlap，相邻块共享文本；查询文本太短时无法区分"自己"与"邻居"。

于是改成分级判定：

| 级别 | 含义 | 处置 |
|---|---|---|
| `exact` | 命中自己 | 理想 |
| `same_doc` | 命中同篇相邻块 | **可接受**：对 RAG 无害，取回的仍是同一篇相关内容 |
| `cross_doc` | 命中别的文档 | **危险信号**：向量或元数据错位 |

**判据是 `cross_doc == 0`，不是 `exact == samples`。** 指标设计要能区分"指标失败"与"系统失败"——3 个 MISS 全落在同篇，说明是指标太严，不是系统坏了。

### 6.3 语义检索（人工探针）

三类探针：药物-结局、指南推荐、中文。


### 6.4 元数据过滤：不报错不算通过

必须检查**返回条目的字段值是否真的满足条件**，只写"没抛异常"不够——过滤字段名写错时 Chroma 可能静默返回全部。

| `where` | 返回条字段值 | 结论 |
|---|---|---|
| `{"lang":"en"}` | `['en','en']` | PASS |
| `{"lang":"zh"}` | `['zh','zh']` | PASS |
| `{"is_table":true}` | `[True,True]` | PASS |
| `{"pub_year":"2023"}` | `['2023','2023']` | PASS |

### 6.5 边界情况

| 输入 | 结果 |
|---|---|
| 空查询 `""` | 不报错，返回 sim 0.6215 |
| 纯空格 | 同上 |
| 超长（约 6000 字符） | 不报错，sim 0.5925 |
| 无意义串 `asdfghjkl` | 不报错，sim 0.4754 |

**真发现**：空查询仍返回结果——Ollama 对空串也给出非零向量，Chroma 照常检索。不崩溃，但危险：**r3 生成层必须加非空校验**，否则空查询会把无关片段塞进上下文污染答案。

## 7 故障复盘：一次真实的"服务退化"

### 7.1 现象

速率从 1.9 块/s 掉到 0.8 块/s，日志出现：

```
12 480 块前：稳定 ~1.9 块/s
12 480 块后：[retry 1/3] ReadTimeout: timed out
             [retry 2/3] ReadTimeout: timed out     ← 吃掉了约 2 小时
13 632 块时：[retry 1/3] ResponseError: 502
```

### 7.2 诊断路径（可复用）

| 步骤 | 动作 | 结论 |
|---|---|---|
| 1 | 看日志找**速率拐点** | 定位到 12 480 块处突变，之前一直稳定 |
| 2 | 排除其他进程 | 另外两个 Python 是 VS Code 的 jedi 语言服务（14 MB / 12 MB），不占 CPU |
| 3 | 检查内存 | 27.8 GB 中可用 10.6 GB，无压力 |
| 4 | **单独探测服务** | 32 块耗时 **42.7 s**（健康时应 2.7 s）→ 确认是服务侧退化，不是脚本问题 |
| 5 | 查进程运行时长 | Ollama 主服务已连续运行 5 天（9/16 启动）→ 长跑后挂起 |

关键在第 4 步：**不要猜，去测。** 单独发一次请求，就把"脚本慢"和"服务慢"分开了。

### 7.3 修复

1. `timeout` 600 s → **120 s**（脚本 `OllamaEmbedder.__init__`）
2. 停嵌入进程 → 重启 Ollama → 从断点 14 080 续跑

重启后 32 块 **2.7 s**（vs 退化时 42.7 s），恢复正常。

### 7.4 三条教训

| 教训 | 说明 |
|---|---|
| 长跑必须打印速率与 ETA | 否则无法回答"它是什么时候开始变慢的"，只能干等 |
| 必须有断点续跑 | 本次保住了 14 080 块 ≈ 2 h 的成果；重头再来代价不可接受 |
| **超时要短** | 600 s 时一次故障吃掉 2 h；120 s 时最多 6 min（3 次重试）就报错退出，人能及时介入 |
