> 检索系统开发第二部分（BM25 关键词路 + 向量多路 + 三种融合策略 + cross-encoder 多准则重排序）

## 0 符号与参数词典

| 符号 | 含义 | 本文取值 |
|---|---|---|
| $Q$ | 用户原始查询 | 中/英自然语言 |
| $Q'$ | 第一部分增强结果 `EnhancedQuery` | 含 `variants` / `keyword_query` / `filters` |
| $D$ | 文档块全集 | $\|D\| = N = 27\,349$ |
| $s_{vec}(d)$ | 向量路得分（余弦相似度） | $\in [-1, 1]$，实测集中在 0.4~0.75 |
| $s_{bm}(d)$ | BM25 得分 | 无上界，实测 0~30 |
| $R_i$ | 第 $i$ 路返回的排序列表 | 每路 top-$k$ |
| $\mathrm{RRF}_k(d)$ | 倒数排名融合分 $\sum_i \frac{1}{k + \mathrm{rank}_i(d)}$ | $k = 60$ |
| $w$ | 融合权重 | `vector` 0.7 / `keyword` 0.3 |
| $p_{rel}(d)$ | cross-encoder 相关性概率（sigmoid） | $\in [0,1]$ |
| $c_{rel}, c_{rec}, c_{auth}$ | 相关性 / 时效性 / 权威性准则分 | 均压到 $[0,1]$ |
| $C(d)$ | 重排序最终分 | $0.6\,c_{rel} + 0.25\,c_{rec} + 0.15\,c_{auth}$ |

## 1 环境约束（先探后做）

这一层的可行性几乎完全由环境决定——**cross-encoder 是 CPU 上的重计算**，不先摸清约束就动手会白花几小时。

| 约束 | 实测 | 对方案的影响 |
|---|---|---|
| GPU | `torch.cuda.is_available() = False`，CPU 8 线程 | cross-encoder 只能作用于召回后的几十条，不能全库跑 |
| `transformers` | 未安装 → 装 5.19.0 | 模型加载 4.6 s（278M） |
| 模型获取 | **HF 主站大文件被 TLS 中断**（`SSL UNEXPECTED_EOF`） | 改走 ModelScope，0.9 MB/s，约 18 min 下完 1 060.7 MB |
| 磁盘 | 可用 444 GB | 1.06 GB 权重可放，但入 `.gitignore`（可从 ModelScope 重下） |
| Ollama | 运行中，提供 bge-m3 查询嵌入 | 向量路延迟主要由它决定（见 §6.3） |

**关于模型获取受阻**：`huggingface.co` 小文件可达（tokenizer 25.6 s 下完），但权重文件在传输中被重置。`hf-mirrors.com` 不可达。最终用 ModelScope 的 `repo?FilePath=` 接口直连下载，并写了 **Range 续传**（1 GB 中断后重头下太亏）。

> 复现提示：`models/` 已被 `.gitignore` 忽略。换机器执行 `scripts/` 下的流水线脚本时若报找不到模型，需重新下载（命令见 §9）。

## 2 BM25 索引

### 2.1 三个实现取舍

| 决策 | 理由 | 依据 |
|---|---|---|
| **自己实现，不用 `rank_bm25`** | 后者把语料放内存且不支持持久化；27 349 块每次启动重建不划算 | 构建耗时 5.7 s，但每次进程启动都付没必要 |
| **postings 用 CSR 扁平数组** | `list[tuple]` 方案约 500 MB；CSR 方案 **29.4 MB** | 实测 3 155 148 条 posting |
| **中文用单字 + bigram，不引 jieba** | 语料 27 196 en / 153 zh（99.4% 英文）；中文只需能匹配上，不值得为分词器加依赖 | 阶段③统计 |

### 2.2 分词

- 英文：`[a-z0-9]+(?:[-'][a-z0-9]+)*`，保留连字符（`covid-19`、`sglt2`），去停用词，长度 ≥ 2
- 中文：连续汉字串拆单字 + 相邻 bigram（`二甲双胍` → `二/甲/双/胍/二甲/甲双/双胍`）
- **停用词复用 `query_understanding.STOPWORDS`**：建索引与查索引必须用同一套过滤规则，否则查询里的 `the/of` 会匹配不上（建时过滤了、查时没过滤）

### 2.3 索引参数与规模

$$s_{bm}(d) = \sum_{t \in q} \mathrm{idf}(t) \cdot \frac{tf(t,d)(k_1+1)}{tf(t,d) + k_1\left(1 - b + b\frac{|d|}{\mathrm{avgdl}}\right)}$$

| 项 | 值 |
|---|---|
| $k_1$ / $b$ | 1.5 / 0.75（Robertson 经典值） |
| 文档数 $N$ | 27 349 |
| 词表 | 142 925 |
| posting 总数 | 3 155 148 |
| avgdl | 167 token |
| 索引文件 | 29.4 MB（`data/bm25/bm25_index.pkl`，已忽略；`bm25_meta.json` 入库） |
| 构建耗时 | 5.7 s |
| 查询耗时 | 毫秒级（`np.bincount` 累加，非全库扫描） |

中英文各验一条（BM25 单独查询）：

```
metformin cardiovascular mortality   → 21.65 / 18.99 / 16.70 ...
二甲双胍 心血管                        → 命中 4 条（bigram 生效）
```

### 2.4 一个必须处理的差异：BM25 没有 `where`

向量路由 Chroma 原生支持 `where` 元数据过滤；BM25 是自己实现的，没有过滤能力。若不过滤，时间约束（如"2020年以后"）在关键词路上会失效，融合后污染结果。

处理：BM25 返回候选后，用 `DataFrame` 补齐元数据再剔除不合规项（`_apply_filter()`）。实测带时间约束查询的年份合规率 100%。

## 3 多路检索与融合

### 3.1 为什么要两路

| 路 | 怎么找 | 死穴 |
|---|---|---|
| 向量（bge-m3） | 按"意思"找 | 罕见词、精确编号（`eGFR < 30`、`SGLT2`）被语义平均掉 |
| BM25 | 按"字面"找 | "心梗" 找不到 `myocardial infarction` |

两路死穴互补，这是多路召回成立的前提。

### 3.2 实际是 3~4 路，不是 2 路

第一部分产出的 `variants`（含中文原句 A、纯英文术语串 C 等）每条都单独检索一次，再加 BM25 一路：

```
vec0  中文原句      → top-k
vec1  英文术语串    → top-k
bm25  keyword_query → top-k
```

这不是设计冗余：第一部分消融已证明中文查询的最优策略不可预测（4 条里 A 赢 1 次、B 赢 1 次、C 赢 2 次），所以不赌单一策略。

### 3.3 三种融合策略

| 策略 | 做法 | 为什么需要它 / 它的缺陷 |
|---|---|---|
| `simple` | 按路顺序拼接去重 | **基线**。忽略排名与分数，用来量化"排名信息值多少" |
| `rrf` | $\sum_i 1/(60 + \mathrm{rank}_i)$ | **学术检索默认**。两路分数天然不可比（余弦有界、BM25 无界），RRF 只用排名，绕开归一化这个坑 |
| `weighted` | 各路 min-max 归一化后加权（向量 0.7） | 需要分数可比，因此受归一化方式影响 |

`weighted` 的坑在这里：**min-max 归一化把一路内的最高分压成 1.0**，即使那一路整体质量很差。单路命中少时，噪声被放大。

### 3.4 接口

```python
retrieve(query_info, top_k_vector, top_k_keyword,
         fusion_strategy='rrf'|'weighted'|'simple',
         where_filter, rrf_k=60, weights={'vector':0.7,'keyword':0.3})
```

输出每块带 `path_scores` / `path_ranks` / `n_paths`，供重排序与生成层追溯"这块是被哪几路命中、各排第几"。

## 4 实验 A：融合策略对比（结果反直觉）

### 4.1 结果

用 cross-encoder 给候选池打分（top1 / top5 relevance），6 条查询：

| 查询 | rrf | weighted | simple |
|---|---|---|---|
| 二甲双胍对心血管疾病有何影响？ | 0.9759 / 0.5081 | 0.9759 / 0.7003 | 0.9759 / **0.4129** |
| MI 患者的死亡率 2020年以后的研究 | 0.9935 / 0.6117 | 0.9935 / 0.6737 | 0.9424 / **0.7095** |
| Does metformin reduce cardiovascular mortality... | 0.9631 / 0.7215 | 0.9975 / 0.2542 | 0.9975 / **0.9084** |
| SGLT2 inhibitor heart failure hospitalization | **0.1334** / 0.6987 | 0.9197 / 0.6069 | 0.9740 / 0.6436 |
| 近五年关于慢性肾病eGFR的随机对照试验 | 0.5347 / 0.2618 | 0.5347 / 0.2560 | 0.2950 / 0.2109 |
| 抗生素治疗社区获得性肺炎的疗程 | 0.3040 / 0.0669 | 0.3040 / 0.0667 | 0.3040 / 0.1009 |
| **top5 均值** | **0.4781** | 0.4263 | **0.4977** ← 最高 |

**反直觉点：任务书推荐的 RRF 排第二，"基本方法" simple 反而最高。**

### 4.2 为什么 simple 会赢——它不是更好，是"退化"了

`simple` 按路顺序拼接，取前 20 时几乎全是 `vec0` 的 top20，等于**只保留向量路**。而 rrf / weighted 会把 BM25 的候选混进来，其中相当一部分 relevance 低，拉低了均值。

所以这个指标实际在奖励"保守"、惩罚"探索"。

### 4.3 BM25 到底有没有增量价值（补充实验）

如果 BM25 只是噪声，那丢弃它的 simple 就该赢。必须单独测：

| 查询 | BM25 独有候选 | 其中最高 rel | 向量 top20 均值 | 超过均值的条数 |
|---|---|---|---|---|
| 二甲双胍对心血管疾病有何影响？ | 18 | 0.9976 | 0.4990 | 2/18 |
| MI 患者的死亡率 2020年以后的研究 | 9 | 0.9278 | 0.5470 | 3/9 |
| Does metformin reduce cardiovascular... | 16 | 0.9982 | 0.7615 | 2/16 |
| SGLT2 inhibitor heart failure... | 18 | 0.9495 | 0.4126 | 3/18 |
| 近五年关于慢性肾病eGFR... | 8 | 0.6768 | 0.2391 | 3/8 |
| 抗生素治疗社区获得性肺炎的疗程 | 20 | 0.0506 | 0.1202 | **0/20** |

**结论：BM25 确实带来向量路漏掉的高相关候选**（每条 2~3 条，最高 rel 0.998）。所以 simple 不是"更好"，是**丢掉了这些增量**。

**反面证据也保留**：最后一条（抗生素）0/20——BM25 在这条上完全无效。原因是第一部分的 `keyword_query` 对该查询的术语覆盖不足，关键词串质量差，BM25 自然检索不到。**BM25 这一路的上限受上游查询增强质量制约**，不是独立模块。

**关于本节数字的时效性（补记）**：写完之初，BM25 路有个缺陷——"后置过滤先取 top_k 再筛"，年份过滤下 20 条只剩 8~11 条，等于变相砍掉这一路。改成 over-fetch（先取 5 倍再筛，恢复到 20 条）之后，§4.1 / §6 的表**全部重跑了一遍**，结果与修复前完全一致（0.4781 / 0.4263 / 0.4977，Δtop1 +0.1980 均未变）。

这说明：**候选池 top5 relevance 这个指标对"BM25 路多带多少候选"并不敏感**——补充进来的 BM25 候选大多排不进融合后的前 5。但修复仍然是必要的：它恢复的是候选池的**规模与来源多样性**，只是这个值恰好测不出来。删掉它是错的，用这个指标证明它有用同样不可靠。

### 4.4 融合策略的差别会被重排序抹平吗

既然融合排序误差可以由 cross-encoder 纠正，那策略选择还重要吗？

| 查询 | 策略 | 融合 top1 | 重排后 top1 | 重排后 top5 均值 |
|---|---|---|---|---|
| 二甲双胍 | rrf | 0.9759 | 0.9979 | 0.9645 |
| 二甲双胍 | weighted | 0.9759 | 0.9979 | 0.9666 |
| 二甲双胍 | simple | 0.9759 | 0.9946 | 0.9600 |
| metformin | rrf | 0.9631 | **0.9975** | 0.9877 |
| metformin | weighted | 0.9975 | **0.9975** | 0.9812 |
| metformin | simple | 0.9975 | **0.9975** | 0.9903 |
| SGLT2 | rrf | **0.1334** | **0.9953** | 0.9211 |
| SGLT2 | weighted | 0.9197 | **0.9953** | 0.9442 |
| SGLT2 | simple | 0.9740 | **0.9953** | 0.9070 |

融合阶段的 top1 差异极大（SGLT2：0.1334 vs 0.9740，相差 0.84），**重排后三策略的 top1 完全相同**（0.9953 / 0.9953 / 0.9953；metformin 三条也都是 0.9975）。

**结论：重排序几乎完全抹平了融合策略的差异。** 它把 §4.1 里 rrf 那条 0.1334 的 top1 直接拉到 0.9953，也让 simple 与 rrf 的差距消失。

**另一个值得注意的反转**：重排后的 top5 均值是 `weighted 0.9640 > rrf 0.9578 > simple 0.9524`，与召回阶段（simple 0.4977 > rrf 0.4781 > weighted 0.4263）**排序相反**。指标结论随阶段翻转，恰好说明单靠一个代理指标无法给策略排名次。

### 4.5 默认策略的选择与保留的意见

默认仍用 **`rrf`**，理由：利用排名信息、`weighted` 有归一化放大噪声的已知缺陷、`simple` 会丢掉 BM25 增量（§4.3）。

但必须写明：**这个选择在本次实验指标下并非最优**（simple 的 top5 均值更高）。判定需要标注集，当前指标（平均 relevance）对"探索型"策略不公平。三种策略都保留为可切换参数。

## 5 重排序器设计

### 5.1 为什么需要它

| | 召回（双塔） | 重排序（cross-encoder） |
|---|---|---|
| 编码方式 | query 与 doc 各自独立编码 | query 与 doc 拼在一起过模型 |
| 交互深度 | 浅（只有向量比对） | 深（词级交互） |
| 代价 | 可全库检索 | 必须逐条推理，**只能作用于召回后的几十条** |

### 5.2 模型

`BAAI/bge-reranker-base` = `XLMRobertaForSequenceClassification`，278M 参数，加载 4.6 s。tokenize → 推理 → `sigmoid(logits)` 得概率。

### 5.3 三个准则的取值依据

三个准则**必须先压到同一量纲再加权**，否则 0.6 / 0.25 / 0.15 的权重没有意义（会被量纲吃掉）。

| 准则 | 取值 | 为什么这么取 |
|---|---|---|
| $c_{rel}$ | cross-encoder 概率，**在候选集内 min-max 归一化** | 原始概率跨查询不可比（同一批可能全在 0.02~0.3）。不归一化时，0.6 的权重表达不了"相关性最重要" |
| $c_{rec}$ | $(y - 1992)/(2026 - 1992)$，缺失取 0.5 | 线性衰减，参考系固定为语料年份范围，避免不同批次候选集漂移；缺年份给中性值，不惩罚也不奖励 |
| $c_{auth}$ | $0.4 + 0.6 \cdot \frac{\log(1+n_j)}{\log(1+n_{max})}$，顶刊 +0.15 | **没有 JCR / 影响因子数据**，只能用"该期刊在本语料的发文量"作代理（发文多 = 该领域主力期刊），再对顶刊白名单（30 种）加成 |

**$c_{auth}$ 的局限必须写明**：它是启发式，不是真实权威性。§6.2 的消融给出了反面案例——加入权威准则后，top1 从 `Cardiovasc Drugs Ther`（心血管药物专刊）变成 `Foods`（食品科学期刊），因为 `Foods` 在本语料中发文量更大。**代理指标会误导**，这是已知缺陷（见 §10）。

### 6.1 B：重排序收益（同一候选池，重排前后）

| 二甲双胍 | 0.9759 | 0.9979 | +0.0221 | +0.4339 |
| MI 死亡率 | 0.9935 | 0.9935 | +0.0000 | +0.3329 |
| metformin | 0.9631 | 0.9975 | +0.0344 | +0.2633 |

| 抗生素肺炎 | 0.3040 | 0.3040 | +0.0000 | +0.0551 |

SGLT2 那条是最强证据：融合排序把一条 relevance 仅 0.1334 的候选排在第一（BM25 路 rank1 被 RRF 过度奖励），**重排序把它换成 0.9953**。

两条 Δtop1 = 0 的查询，是因为融合 top1 本身已是候选池内最优。

## 7 工程决策：为什么 int8 量化默认关闭

CPU 上重排序是瓶颈，所以扫了参数与量化（20 条候选）：

| max_length | batch | 耗时 s | ms/条 | top1 | top5 均值 |
|---|---|---|---|---|---|
| 128 | 8 | 3.13 | 156 | 0.9871 | 0.7418 |
| 256 | 8 | 6.26 | 313 | 0.9104 | 0.6700 |
| 512 | 8 | 12.11 | 606 | 0.9631 | 0.7215 |
| 512 | 16 | 11.46 | 573 | 0.9631 | 0.7215 |
| **512 + int8 量化** | 8 | **5.78** | **289** | 0.9876 | — |

量化快 **2.1 倍**，看着很诱人。但默认开启前必须验证它不改结果：

| 查询 | top5 重合 | top10 重合 | 分数相关 | 最大绝对偏差 |
|---|---|---|---|---|
| metformin | **3/5** | 9/10 | 0.7765 | **0.5008** |
| MI 死亡率 | 5/5 | 8/10 | 0.8778 | 0.4747 |
| SGLT2 | **4/5** | 9/10 | 0.9089 | **0.5358** |

**结论：不默认开启。** top5 有 20% 的条目被替换，分数最大偏差 0.47~0.54——12 层 int8 近似误差被放大后足够改写排序。重排序是最后一道质量关，不该为省 6 秒牺牲 top5。

实现为 `BGEReranker(quantize=True)` 开关，默认 `False`，代码注释里留了这组实测数据。

另：batch_size 从 8 到 16 几乎无提升，说明瓶颈是计算量而非调度，默认 8（内存更稳）。

## 8 完整检索流水线

```
用户查询
  ↓ enhance_query()              第一部分：缩写/中英/过滤      ~10 ms
  ↓ MultiPathRetriever           向量 2~3 路 + BM25 1 路      ~8.5 s
  ↓ 融合（默认 rrf）               20~40 条候选                毫秒级
  ↓ BGEReranker                  cross-encoder + 三准则        ~660 ms/条
  ↓ 证据列表（带 doc_id/journal/pub_year/pmid）
```

`scripts/retrieval_pipeline.py`：

```bash
python scripts/retrieval_pipeline.py "二甲双胍对心血管疾病有何影响？"
python scripts/retrieval_pipeline.py "metformin cardiovascular" --json
python scripts/retrieval_pipeline.py "MI 死亡率" --no-rerank --fusion weighted
```

输出每条含 `rank / score / criteria / path_ranks / text / metadata`，并附 `timing`（增强 / 召回 / 重排分段耗时），便于定位瓶颈。

**这一层输出的是"证据清单"，不是答案**——医学场景每条必须带 PMID / 期刊 / 年份，否则下游生成无法溯源。

## 10 遗留与下一步

| 项 | 问题 | 建议 |
|---|---|---|
| **标注集** | 最关键。所有"是否更相关"的结论都用 cross-encoder 自评，存在自证偏差，算不了 Recall@K / MRR | 20~30 条 (问题, 相关块)，采样覆盖缩写/中英/时间约束三类 |
| **authority 准则** | 用发文量代理权威性，`Foods` 案例证明会失效 | 接入 JCR 影响因子或期刊白名单表；否则考虑降到 0.1 或关闭 |
| **融合策略** | 实验指标下 simple 最优但会丢 BM25 增量，需要标注集才能定论 | 标注集到位后重跑 §4 |
| **量化 / 加速** | int8 会改排序；ONNX Runtime 已在依赖里（1.23.2），未测 | 测 ONNX + 静态量化，对比 top5 重合率 |
| **延迟** | 15~22 s/查询，其中召回 8.5 s 是 Ollama 查询嵌入 | 变体路可并行；或缓存高频查询 |
| **BM25 依赖上游** | 抗生素查询 0/20，因 `keyword_query` 术语覆盖不足 | 补词典（第一部分 §11） |
