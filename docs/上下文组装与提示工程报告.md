## 1 先探环境：这一层的可行性完全由 LLM 决定

写完这一层才敢说：**这三个组件的设计几乎是被环境逼出来的**。动手前先探的几项：

| 探测项 | 实测 | 带来的设计约束 |
|---|---|---|
| 可用 LLM | `deepseek-r1:7b`（4.7 GB），只有这一个 | 无备选，全部围绕它设计 |
| 生成速度 | **6.3~6.6 tokens/s** | 单阶段实测 **160.8 秒**；四阶段串联约 **10~15 分钟** |
| thinking | **无法关闭**（实测 `think=False` 无效），占 60~70% token | `max_tokens` 是"thinking + 正文"的总预算 |
| `num_predict=150` | **答案为空**（thinking 把预算用完） | 最小预算必须 ≥800，否则拿到空答案 |
| prompt 处理速度 | ~19 tokens/s（1027 token 用 52.8 s） | 上下文必须限长，否则光读就要一分钟 |
| `num_ctx` 默认值 | 2048 | 必须显式设 **8192**，否则超长部分被**静默截断** |
| token 计数接口 | `/api/tokenize` 返回 **404**；python client 无 `tokenize` | 只能本地估算（§2.2） |

**三条最硬的约束**：thinking 关不掉、没有 token 计数接口、上下文会被静默截断。下面每个设计都是绕开它们。

## 2 上下文组装器

### 2.1 为什么检索结果不能直接塞进 prompt

三件事必须先处理：

1. **重复**：同一篇文献的相邻块高度重叠，全塞进去浪费配额还稀释重点
2. **视角窄**：top-k 里可能 5 条有 3 条来自同一篇
3. **超窗**：超过 `num_ctx` 会被**静默截断**——末段证据凭空消失，且**不报错**

### 2.2 token 估算：没有计数接口，只能自己校准

`get-tokenizer` 这条路走不通（§1）。所以反过来用模型当标尺：发一段已知文本给 `deepseek-r1:7b`，读它返回的 `prompt_eval_count`，反推"字符/token 比"。

校准结果：

| 文本类型 | 字符 | 实际 token | 字符/token |
|---|---|---|---|
| 中文 | 300 | 191 | **1.57** |
| 英文 | 760 | 151 | **5.03** |

估算式：

$$\hat{t}(x) = \left(\frac{\text{汉字数}}{1.57} + \frac{\text{非汉字数}}{5.03}\right) \times 1.3$$

#### 一个必须记下来的坑

按上式估算一段真实上下文：

```
上下文 12042 字符  →  估算 2418 token
模型实际计入        →  3147 token
偏差               →  -23.2%（低估）
```

**为什么会低估**：校准用的是纯中/英文散文，但真实上下文里混着 `PMC11219383` 这**类文献号、年份、斜杠、编号表头**。数字和符号会被分词器拆得远比散文碎。

**为什么低估很危险**：低估意味着按估算"装满了预算"，实际却超出 23% → 触发**静默截断**，末尾证据悄无声息地消失。

**修法**：加安全系数 **1.3**（宁可估大）。修正后复测：

```
估算 2448  →  实际 2451  →  偏差 -0.1%
```

**教训**：校准样本必须和目标数据形态一致。用"纯散文"校出来的系数，套到"带大量 ID 和符号"的文本上必然偏。

### 2.3 去重：Jaccard + 字符 n-gram

**为什么用字符 n-gram 而不是词**：
- 中文没有空格，分词得引 jieba（不值得）
- 英文里 `metformin` 和 `metformin.` 应视为相同 → 字符级天然免疫标点差异

实测（阈值 0.7）：

| 变体 | Jaccard | 判定 |
|---|---|---|
| 完全相同 | 1.0000 | 丢弃 |
| 仅差标点空格 | 1.0000 | 丢弃 |
| 轻微改写字序 | 0.6462 | **保留** |
| 不同内容 | 0.0052 | 保留 |

"改写字序" 0.65 被保留是**想要的行为**——那确实是不同表述，不是重复。

端到端：4 条高度相似块 → 去重后 **1 条**。

#### 但真实候选里，去重一次都没触发

预算表里"去重丢 0 条"到底是因为**没有重复**，还是因为**阈值太松**？两者结论完全相反，必须查清楚。统计 40 条真实候选中同一文献的块两两相似度：

```
40 条候选来自 29 篇，其中 5 篇贡献了 ≥2 块，共 23 组同篇块对
最大相似度 0.1618，均值 0.0708
≥0.3 的 0 组，≥0.5 的 0 组，≥0.7 的 0 组
```

最相似的一对是 `PMC3464381_0001 vs _0000`，也只有 **0.1618**，离阈值 0.7 差得很远。

**结论**：去重丢 0 条是真实的——**不是阈值太松**。原因是第一阶段的分块本身就把相邻块切得足够不重叠。所以：

- 阈值 0.7 在本语料上**不会误删**（真实最高 0.16，安全余量很大）
- 也**不会漏删**（确实没有重复块）
- 它是**防御性设计**：换分块策略、换语料、或逐年增量入库导致同一文献重复进入时才会生效

诚实地说：**这个机制在当前数据上是没有贡献的**，保留它算保险，但它不是本阶段的有效收益。

### 2.4 多样性：同来源软惩罚

第 $n$ 个来自同一文献的块，分数乘以 $0.6^n$，且单篇上限 3 块。

**为什么用软惩罚而不是硬截断**：避免"该文献确实贡献了高质量证据"时被一刀切掉，同时防止单一来源垄断上下文。

实测（4 块来自 A + 1 块来自 B）：

```
纯按分数:  A1(0.95) A2(0.93) A3(0.92) A4(0.91) B1(0.80)
降权后:    A1 → B1(0.80) → A2 → A3      A4 被上限截断
```

B1 从**第 5 位提到第 2 位**，且没有被完全挤出——这正是软惩罚想要的效果。

### 2.5 预算分配与句末截断

逐块累加，超出预算时：
- 剩余预算 ≥ 最小块（80 token）→ 截断该块后塞入
- 否则停止

截断要求"落在完整句子边界"（任务书要求）：先按预算粗取字符，再在**末段 10%** 区域从后往前找句末标点；找不到就整段找，仍找不到才硬截。

实测三档预算，末尾字符都是 `.`：

| 预算 | 截断后 token | 末尾字符 | 落在句末 | 未超预算 |
|---|---|---|---|---|
| 100 | 88 | `.` | ✅ | ✅ |
| 200 | 194 | `.` | ✅ | ✅ |
| 400 | 390 | `.` | ✅ | ✅ |

#### 这里踩过一个自己挖的坑

给 `estimate_tokens` 加安全系数（§2.2）时，**忘了同步截断函数**，两者口径不一致：截断按"真实比例"截，结果用保守估算一量就超。实测预算 100 会截出 **123 token** —— 截了等于没截，照样超窗。

修法是让截断也除以同一个安全系数（保留更少字符）。修复后上表的三档都严格落在预算内。**教训**：同一个"token"概念在代码里出现两次，改一处必须同步另一处，否则安全设计会自己失效。

### 2.6 不同预算下的取舍

| 预算 | 入选 | 估算 token | 去重丢 | 多样性丢 | 预算丢 |
|---|---|---|---|---|---|
| 400 | 3 | 348 | 0 | 3 | 34 |
| 800 | 7 | 797 | 0 | 3 | 30 |
| 1500 | 13 | 1477 | 0 | 3 | 24 |
| **2500** | **21** | **2448** | 0 | 3 | 16 |
| 4000 | 34 | 3962 | 0 | 3 | 3 |

**注意"去重丢 = 0"**：本次 40 条候选里没有重复块。这**不代表去重没用**——重复主要出现在"同一文献的相邻块同时被召回"时，而第二阶段的多样性限制（单篇 ≤3）已经把它挡掉了一部分。所以单独构造了 §2.3 的端到端样例验证它确实工作。

默认 **2500**：在 LLM 的 `num_ctx=8192` 内留出足够空间给 system prompt、问题和答案，同时控制 prompt 处理时间在可接受范围。

### 2.7 输出元数据

```python
{
  "total_chunks_retrieved": 40,        # 检索返回
  "unique_chunks_after_dedup": 40,     # 去重后
  "chunks_selected": 21,               # 多样性筛选后
  "estimated_tokens": 2448,            # 最终上下文估算 token
  "chunk_sources": {...},              # 来源分布 + 年份范围
  "dropped_by_dedup": 0,               # 各环节的丢弃明细
  "dropped_by_diversity": 3,
  "dropped_by_budget": 16,
  "token_budget": 2500
}
```

比任务书要求的多了三项 `dropped_by_*`：**只有知道在哪一步丢了多少，才能判断该调去重阈值还是调预算**。

## 3 DocumentChunk 数据类

```python
@dataclass
class DocumentChunk:
    text: str
    metadata: Dict[str, Any]
    relevance_score: float
    source: str
    chunk_id: str
```

两个设计点：

**分数取值有优先级**：`rerank_score > fused_score > relevance_score`。重排序是最后一道质量关，优先用它；没重排时退到融合分。

**`doc_id` 从 `chunk_id` 拆出来**：`PMC11219383_0007` → `PMC11219383`。多样性控制需要"同一篇文献"这个粒度，而 `source` 字段在不同阶段可能指代 different 东西，所以统一由 `chunk_id` 推导，不另存冗余字段。

## 4 医学提示模板

### 4.1 为什么拆成四个阶段

一次生成写不出可靠答案。拆开的理由是每一环的能力不同：

| 阶段 | 干什么 | 为什么不合并 |
|---|---|---|
| **证据评估器** | 逐条判定是否支持问题、判定研究类型与强度 | 让模型先"筛一遍证据"，避免低质量片段在下一步被当成依据 |
| **答案生成器** | 只用"可用证据"写答案，每句带 `[n]` | 与评估分离，才能确保每条陈述都溯源 |
| **批判性审查器** | 挑出的六大类问题（无引用 / 过度概括 / 跨物种外推 / 因果倒置 / 遗漏限定 / 反向证据被忽略） | LLM 天然倾向说得比证据更肯定，需要一次对抗性检查 |
| **最终组装器** | 吸收意见出终稿 + 来源清单 + 免责声明 | 定稿与挑错职责不同，合并会让自相矛盾 |

### 4.2 每个模板里的三条医学硬约束

1. **不编造**：证据没覆盖的必须明说"现有检索到的证据未涉及此点"
2. **可溯源**：每条结论带 `[n]`，n 对应上下文里的来源编号
3. **有分寸**：措辞强度匹配证据强度——RCT/Meta 用"表明"，观察性研究用"提示"，动物实验必须写明"在动物实验中观察到"

### 4.3 参数取值依据

| 阶段 | temperature | max_tokens | 理由 |
|---|---|---|---|
| 证据评估器 | 0.0 | 1400 | 判定任务要稳定可复现，不给随机性 |
| 答案生成器 | 0.2 | 1600 | 需要一点表达多样性，但远低于默认以防发挥 |
| 批判性审查器 | 0.0 | 1400 | 挑错任务同样要稳定 |
| 最终组装器 | 0.1 | 1600 | 定稿整合，几乎不需要创造性 |

**`max_tokens` 为什么给这么大**：它不是答案长度！`deepseek-r1` 的 thinking **无法关闭**（§1），一次调用里 thinking 约占 60~70% token，而 `max_tokens` 是两段的总预算。实测给 150 时会出现"思考完了、正文一个字没有"的空答案。

### 4.4 一个实现细节：不用 `str.format`

模板渲染用逐变量 `replace`，因为**证据文本里常带花括号**（如给药剂量的写法、`{n=12}`）。`str.format` 会把它们当占位符直接抛 `KeyError`。已验证：含 `{...}` 的证据文本渲染通过。

## 5 端到端生成验证

跑 `answer_generator` 单阶段（检索 → 组装 → 生成），验证模板真能驱动模型产出符合要求的东西。

| 环节 | 耗时 | 说明 |
|---|---|---|
| 检索 + 重排序 + 组装 | 40.4 s | 12 条候选 → 上下文 1406 tokens |
| **生成（仅答案生成器）** | **160.8 s** | 1060 tokens，6.59 tokens/s |
| 合计 | ~201 s | 单阶段完整链路 |

thinking 873 字符 / 答案 814 字符——**thinking 占了大半预算**，再次印证 §4.3 必须给足 `max_tokens`。

### 5.1 产出是否符合模板要求

| 要求 | 结果 |
|---|---|
| 每条结论带 `[n]` 引用 | ✅ 全文 9 处引用，编号 `[3][5][6]` |
| 只使用给定证据 | ✅ 引用编号都在上下文范围内 |
| 中文、结论先行再展开 | ✅ 先总述，再分 8 点展开 |
| 不输出思考过程 | ✅ 未混入 `<think>` |

### 5.2 一处必须指出的可疑陈述（反面证据）

答案第 3 点写道：

> 通过调节 HDL 和 LDL 的水平，**降低高密度脂蛋白胆固醇，同时增加低密度脂蛋白胆固醇**的水平

这在医学上**可疑**——二甲双胍通常被认为降低 LDL，而非升高。同时该段只引用了单一来源 `[6]`，且答案里有 4 个不同机制都引同一条证据 `[6]`。

**这个观察不是 bug，而是设计论证**：单阶段生成会出现
1. 可能的错误陈述；
2. 一条证据被外推到多个机制。

这恰恰是 **批判性审查器** 存在的理由——它的六类检查里，"过度概括""遗漏限定""无引用支持"正对着这两种毛病。**由于 CPU 上四阶段要 10~15 分钟，本次没有跑完整串联**，所以审评阶段能否纠出这条错误，目前**未经验证**，记入 §7 遗留。

### 5.3 延迟的现实约束

单阶段已 160 秒。四阶段串行按此推算约 **10~15 分钟/查询**（且越靠后阶段的输入越长，实际会更久）。所以：

- 演示/评测：跑单阶段或前两阶段
- 要完整质量：接受 10 分钟级延迟
- 后续可考虑：`num_ctx` 与候选数下调、或用非推理模型做定稿阶段

## 7 遗留与下一步

| 项 | 问题 | 建议 |
|---|---|---|
| **四阶段串联未验证** | 单阶段跑了，完整串联因延迟（10~15 分钟）未跑；§5.2 里那条可疑陈述能否被审查器纠出，**未知** | 跑一次 `--full`，人工核对初稿→审查→终稿的差异 |
| **答案事实正确性无法自动评判** | 没有 (问题, 金标准答案) 标注，"引用正确 ≠ 陈述正确" | 需要医学背景 reviewer 或参考答案集 |
| **延迟** | 单阶段 160 s、四阶段 10~15 分钟 | 候选数下调；定稿阶段换非推理模型 |
| **token 估算仍是估算** | 本次数据上修到 -0.1%，但**换一批数据分布可能再偏**（§2.2 的教训） | 定期用 `prompt_eval_count` 复校安全系数 |
| **去重触发率低** | 40 条真实候选里去重丢 0 条，机制没在真实数据上被检验 | 在"同篇相邻块同时召回"的场景下专门验证 |
| **块间关系未利用** | 现在只知道来自哪篇，不知道块在原文中的相邻关系 | 相邻块可合并压缩，进一步省配额 |
