## 1 先探环境：JSON 生成到底听不听话

第二部分的核心动作是"让模型输出 JSON，再提取修复"。动手前先测了这件事的可行性：

| 实验 | 耗时 | tokens | 正文形态 |
|---|---|---|---|
| A. `format='json'`（Ollama 原生约束） | 23.3 s | 141 | ` ```json {...} ``` ` **带代码围栏** |
| B. 不加 format，仅靠 prompt 要求 | 20.5 s | 199 | ` ```json {...} ``` ` **同样带围栏** |

两种方式的正文都是：

```
\n\n```json\n{\n  "evaluations": [...],\n  "usable_ids": [1]\n}\n```
```

**结论：`format='json'` 在这个模型上形同虚设**——它并没有阻止模型套 markdown 围栏，直接 `json.loads` 两种都失败。

所以第二部分真正的活儿不是"调 JSON 模式"，而是**写一个能容忍真实输出的提取修复器**。`format='json'` 保留为可选（tokens 略少），但不依赖它。

## 2 LLMGenerator

### 2.1 初始化与连接测试

```python
LLMGenerator(model_name="deepseek-r1:7b",
             base_url="http://localhost:11434",
             timeout=300, temperature=0.1, max_tokens=1600, num_ctx=8192)
```

`test_connection(quick=False)` 验证：服务可达、模型已拉取、模型能力声明。实测输出：

```json
{"service_ok": true,
 "available_models": ["bge-m3:latest", "deepseek-r1:7b"],
 "model_present": true,
 "capabilities": ["tools", "thinking", "completion"]}
```

`quick=True` 时再跑一次极短生成，验证 `temperature` / `max_tokens` 参数链路确实走得通。

**两个必须前置的设置**（都是之前踩过的坑）：

- `NO_PROXY=localhost,127.0.0.1` **必须在创建 client 之前**。Windows 系统代理写在注册表，`httpx` 默认 `trust_env=True` 会把 localhost 也发给代理 → `WinError 10061`
- `num_ctx=8192`。默认 2048 会**静默截断**上下文

### 2.2 生成方法

按任务书：`prompt + system_prompt + temperature + max_tokens` 构建完整消息，system 按模型格式作为 `system` role 传入。返回结构带：

```
success / content / thinking / raw_text / eval_count / prompt_eval_count /
seconds / tokens_per_s / temperature / max_tokens / error
```

**保留 `thinking` 与 `raw_text` 的原因**：这个模型思考与正文分离，排障时必须能看到"它是想太多还是没答"。`success=False` 时 `error` 会写明"正文为空(thinking 可能吃光了 max_tokens)"。

### 2.3 JSON 提取与修复（本阶段的核心）

`extract_json()` 依次尝试：

```
原文 → 去代码围栏 → 截取括号区间(丢掉前后解释文字)
     → 修尾逗号 / 中文引号 / 控制字符
     → 栈式补全未闭合括号
     → ast.literal_eval(兼容单引号、True/False)
全部失败 → 返回 None（不硬造结构体冒充模型输出）
```

**自检用例**（离线，9 条）：

| 用例 | 结果 |
|---|---|
| 标准 JSON | ✅ |
| 带代码围栏 | ✅ |
| 带解释文字 | ✅ |
| 尾逗号 `{"a":1,}` | ✅ |
| 中文引号 `“二甲双胍”` | ✅ |
| 未闭合（截断） | ✅（**修过一次 bug，见下**） |
| thinking 混入正文 | ✅ |
| 单引号 / True | ✅ |
| 完全不是 JSON | 返回 `None`（如实失败，不编造） |

**真实模型输出验证**：把 §1 里 A、B 两段真实输出喂给提取器，**两段都成功**，得到 `{"evaluations":[...], "usable_ids":[1]}`。

#### 自检抓到的 bug：括号补全第一版是错的

第一版分别统计 `{}` 和 `[]` 的个数补全。对嵌套截断 `{"a":1,"b":[1,2`：

- 只补 `}` → `{"a":1,"b":[1,2}` 仍不合法
- 只补 `]` → `{"a":1,"b":[1,2]` 仍不合法

**两种都得补，且必须后开的先闭**。改成栈式扫描（跳过字符串内部、处理转义），按栈逆序补全，用例才通过。这个 bug 是自检抓出来的，不是等线上出事。

### 2.4 批量生成

`generate_batch()` **顺序执行，不并发**。原因很实际：CPU 上只有一个模型实例，并发只会互相抢核让每条都变慢，还可能导致 Ollama 排队超时。

单条失败不中断整批，失败条目带 `error` 返回。

## 3 MedicalGenerationPipeline

### 3.1 六步流程

```
检索 → 上下文组装
     → (可选)证据评估 + 按评估筛选上下文
     → 答案草稿
     → (可选)批判性审查
     → 终稿（有审查意见才走定稿，否则直接用草稿）
     → 后处理（引用整理 / 来源清单 / 免责声明）
```

### 3.2 评估结果解析与上下文筛选

`parse_usable_ids()` 兼容三种输出形态：

| 形态 | 例子 | 解析结果 |
|---|---|---|
| JSON | `{"usable_ids":[1,3]}`（含围栏） | `[1, 3]` |
| 结论文本 | `可用证据编号：3、5、12` | `[3, 5, 12]` |
| 逐行（v3 模板） | `1 - 支持 - …` / `2 - 无关 - …` | 取"支持/部分支持"的编号 |
| 明确说无可用 | `可用证据编号：无可用证据。` | `[]` |
| 判定词不规范 | `12 - 系统评价/元分析 - …` | `[]` |
| 空 / 乱文本 | — | `None` |

筛选按**编号**进行（`selected_chunks` 的顺序与上下文里 `[n]` 标题行一一对应），并重建上下文文本、更新 token 估算与来源统计。

**三条降级原则**（都是实测逼出来的）：

1. **解析不出可用编号 → 保留全部上下文**。评估器有过"无可用证据"的误报，照它筛会把上下文清空，后面直接无米下锅。所以 `None` 和 `[]` 都按"不筛选"处理，并记 warning——宁可多用几条证据，也不能把流程搞崩
2. **编号与块对不上 → 保留全部**，不筛空
3. **审查失败 → 用草稿；终稿失败 → 也退回草稿**。后处理是纯代码，总能给出结构完整的结果

### 3.3 后处理

不依赖模型，纯代码完成：

- 多余空行 / 行尾空格清理
- 全角引用 `【3】` 统一为半角 `[3]`
- **缺来源清单就自动补上**（从 `selected_chunks` 取 doc_id / 年份 / 期刊）
- **缺免责声明就自动补上**

## 4 测试

### 4.1 fast 模式完整流程（实测）

配置：跳过评估与审查，只跑"检索 → 组装 → 草稿 → 后处理"。

| 阶段 | 耗时 | tokens | 成功 |
|---|---|---|---|
| retrieve_and_assemble | 177.8 s | 0 | ✅ |
| draft_answer | 103.1 s | 572 | ✅ |
| **合计** | **280.9 s** | | |

- 答案 1121 字符，引用来源 12 条
- **后处理生效**：模型原文没有来源清单和免责声明，由代码自动补齐
- 上下文：检索 12 → 入选 12，估算 1406 tokens

**检索段 177.8 s 明显偏慢**（此前同配置约 40 s）。是环境波动（Ollama 嵌入服务长时运行后吞吐下降，阶段④报告记录过同类退化），不是代码改动导致——本次没有改检索代码。

#### fast 模式答案的质量问题（必须记录）

这条答案里出现了：

- "**降低坏血病风险**"——坏血病是维生素 C 缺乏症，与心血管疾病无关，属于术语层面的错误
- "**提高低密度脂蛋白胆固醇**水平"——与常识相反的可疑表述
- "**MG3-**和 MCI 相关的患者"——`MG3` 含义不明，疑似编造
- "**戒烟辅助**"——二甲双胍与戒烟无直接关联

**这正是 fast 模式的代价**：没有评估筛选、没有审查，这些表述原样出现在最终答案里。后处理只能补格式，**补不了事实**。

### 4.2 完整四阶段流程（实测）

同一查询，开启评估与审查：

| 阶段 | 耗时 | tokens | 成功 |
|---|---|---|---|
| retrieve_and_assemble | 63.3 s | 0 | ✅ |
| evidence_evaluation | 187.7 s | 665 | ✅ |
| draft_answer | 130.2 s | 818 | ✅ |
| critical_review | 126.9 s | 832 | ✅ |
| final_assembly | 156.5 s | 1000 | ✅ |
| **合计** | **664.6 s（11.1 分钟）** | 3315 | |

**评估筛选确实生效**：评估器逐条给出 12 行判定（v3 简化模板），输出可用编号 `[3,4,5,6,8,9,10,12]`，上下文由 **12 块筛到 8 块**，估算 token 由 1406 降到 **936**。

#### fast vs 完整：这次完整模式明显更好

| 项 | fast（仅草稿） | 完整四阶段 |
|---|---|---|
| 总耗时 | 280.9 s | 664.6 s |
| 答案长度 | 1121 字符 | 848 字符 |
| 引用来源 | 12 条 | 8 条（经评估筛选） |
| **可疑表述** | "降低**坏血病**风险"、"**提高**低密度脂蛋白"、含义不明的"MG3-" | **均未出现**；血脂表述为"降低低密度脂蛋白胆固醇和甘油三酯" |

多花 2.4 倍时间，换来的是错误表述消失。**这与上一阶段"四阶段引入新错误"的观察并不矛盾，而是说明：四阶段的收益不稳定，需要更多查询才能下结论**。本次只有 1 条查询，不能推广。

### 4.3 测试中抓到的 bug：筛选后引用错位

完整流程的答案里出现了 `[12]` 这样的引用，但筛选后来源列表只有 8 条——**`[12]` 是悬空引用**。

原因：`_filter_context` 重建上下文时按 `1..k` **重新编号**，而评估文本里的编号是筛选前的（1~12）。模型看到新上下文（1~8）和评估文本（含 12），就在答案里引用了旧编号。

**修法：筛选后保留原编号**，允许编号不连续（`[3][4][5][6][8][9][10][12]`），使上下文标题行、评估文本、答案引用、来源列表四者一致。原编号写入 `metadata["_ref"]`，`_format_sources` 优先读取。

离线验证（不依赖模型，秒级）：

```
上下文标题行编号: ['3','4','5','6','8','9','10','12']
sources 的 ref:   [3, 4, 5, 6, 8, 9, 10, 12]
答案若引用 [12], 是否有对应来源: True
异常编号[99]   -> 保留 12 块（不筛空）
解析失败 None  -> 保留 12 块
无可用证据 []  -> 保留 12 块
```

**教训**：筛选类操作改变编号体系时，要同步考虑"谁还在用旧编号"。这里是评估文本在用，所以不能重排。
