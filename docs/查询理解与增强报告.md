# 查询理解与增强报告

- 生成时间: 2026-09-29
- 处理脚本: `scripts/query_understanding.py`（理解与增强）、`scripts/bench_query_enhancement.py`（对照实验与消融）
- 输入: 用户自然语言查询（中/英），如「二甲双胍对心血管疾病有何影响？」
- 输出: `EnhancedQuery`——清洗后查询、医学实体、同义扩展、向量查询、关键词查询、过滤条件、多版本查询
- 依赖: 阶段④索引 `data/chroma/`（27 349 块 / 1024 维 / bge-m3）
- 数据范围: full（语料 27 196 块 en + 153 块 zh）
- 相关文档: `docs/向量化与索引构建报告.md`（阶段④）

## 0 符号与参数词典

| 符号 | 英文 | 中文 | 形状 / 直觉 |
|---|---|---|---|
| $Q$ | raw query | 原始查询 | 字符串，用户实际输入，可能含缩写/中文/时间约束 |
| $Q'$ | cleaned query | 清洗后查询 | 字符串，仅做全角转半角与空白压缩 |
| $E$ | entities | 医学实体集 | 字典，类型 → 命中的表层形式，如 `{"condition": ["mi"]}` |
| $C$ | canonical terms | 规范术语 | 列表，实体映射到的标准名，如 `["myocardial infarction"]` |
| $S$ | synonyms | 同义词集 | 字典，规范术语 → 同义词列表 |
| $F$ | filters | 过滤条件 | 字典，直接可传给 Chroma 的 `where` |
| $V$ | variants | 查询变体 | 列表，多路召回的每一路输入 |
| $A(Q)$ | enhancement | 增强函数 | $A(Q) = (Q_v, Q_k, F, V)$，本模块的主入口 `enhance_query()` |
| $\text{sim}$ | similarity | 相似度 | Chroma 返回 $1-\delta$，越大越相关 |

关键直觉：**增强不是"把查询改写得更好看"，而是把自然语言里隐含的检索指令显式化**——哪些词要展开、要用哪国语言检索、结果要落在什么范围内。

## 1 为什么必须有这一层

不做增强直接拿 $Q$ 去检索，有四类可预见的失效。每一类都能在语料统计里找到依据：

| 失效类型 | 现象 | 后果 | 依据 |
|---|---|---|---|
| **缩写** | 用户写 `MI`，语料主要写 `myocardial infarction` | 向量空间中两者距离远；`mi` 在英文里还可能是 Michigan / milliliter | 缩写不展开时，检索等价于用噪声向量做查询 |
| **中英** | 用户用中文提问，语料 99.4% 是英文 | 中文查询向量与英文块向量不在同一语义区域的同一位置 | 语料 27 196 en / 153 zh（`index_stats.json`） |
| **时间约束** | 用户说「2020年以后」，Chroma 只认 `{"pub_year": ...}` | 无法回答时间限定问题；不做提取则只能全库检索 | `pub_year` 取值 1992–2026 |
| **单点语义** | 一条查询只命中语义空间的一个点 | 措辞不同就召回不同，稳定性差 | 需多路召回 + 融合（第二部分） |

这四类不是理论推演——§7 的对照实验会给出各自的量化改善幅度。

## 2 词典设计：两层，且标注来源

任务书建议"从 UMLS、MeSH 等标准术语库构建"。**本阶段没有采用**，理由是：UMLS 需要签署 license 才能下载，MeSH 需额外解析；本项目要求离线可复现，第三方跑 `git clone` 后必须能直接运行。改为两层自建：

| 层 | 规模 | 来源 | 特点 |
|---|---|---|---|
| **curated** | 43 个概念组 / 125 个表层别名 / 52 条中文映射 / 18 条缩写 | 人工精选，中英对照 | 高质量、可控，覆盖心血管/代谢/感染/肾病等常见概念 |
| **corpus** | 原始 43 334 条 → 过滤后 **42** 条 | 本项目语料挖掘的 `corpus_acronyms.csv` | 数据驱动：扩展出来的词确实在本库出现过 |

**为什么做数据驱动这一层**：curated 只能覆盖常见术语，而这份表是从**本项目的 1 006 篇文献**里挖出来的真实缩略语（带频次），用它扩展不会凭空造词。

**过滤条件**（`load_corpus_acronyms()`）：

| 闸门 | 阈值 | 理由 |
|---|---|---|
| 频次 | `count >= 500` | 低于此值多半是极窄领域用法或挖掘噪声 |
| 长度 | 5–40 字符 | 过短是截断残片，过长是整句误判 |
| 首词长度 | $\ge 3$ | 排除 `AD → "s disease"` 这类被截断的展开 |
| 字符 | 无制表符 / 反斜杠 / 数字 | 排除表格残留 |

### 2.1 一个必须记录的质量问题

过滤后仍存在**释义错误**的条目：

```
BP → biological process      ← 医学场景下应为 blood pressure
```

频次闸门能滤掉截断噪声，滤不掉"缩写在不同学科有不同释义"这个问题。缓解办法是**优先级**：

```python
# query_understanding.py · expand_synonyms()
if tok in expansions or tok in MEDICAL_ABBREVIATIONS:
    continue          # curated 已覆盖的缩写，绝不用 corpus 的释义覆盖
```

即 `BP` 命中 curated 的 `blood pressure` 后直接跳过 corpus。但**未被 curated 覆盖的缩写仍可能引入噪声**，这是已知局限（见 §11）。

输出里用 `provenance` 字段标注每个术语来自 `curated` 还是 `corpus`，便于下游按置信度加权。

## 3 处理流程

$A(Q)$ 分五步，每步都明确"做什么"和"不做什么"：

| 步 | 做什么 | **不做**什么 | 为什么 |
|---|---|---|---|
| 1 清洗 | 全角→半角、压缩空白 | **不去标点、不去停用词、不改大小写** | §7.2 有实验：去句尾 `?` 会让相似度下降；大写是缩写识别的唯一线索 |
| 2 语言检测 | 按 CJK 字符占比判 `zh` / `mixed` / `en` | 不做翻译 | 无翻译模型；改用术语桥接（§7.3） |
| 3 实体识别 | 正则 + 词典双路 | 不做分词/NER 模型 | 规则可查证、零依赖；医学术语封闭性强 |
| 4 同义扩展 | 缩写展开 + 中英映射 | **不把同义词堆进向量查询** | 堆砌会稀释语义重心；同义词只进变体与关键词路 |
| 5 生成 | 向量查询 / 关键词查询 / 过滤 / 变体 | 不做检索 | 检索在第二部分，此处只产出入口 |

## 4 实体识别：为什么 `MEDICAL_PATTERNS` 用 `\b`

任务书示例里明确要求"使用单词边界 `\b` 确保完整匹配，避免匹配到 `aspirin` 中的 `pirin`"。四类模式：

| 类型 | 覆盖 | 例 |
|---|---|---|
| `drug` | 药物 | `metformin` `aspirin` `statin` `sglt2 inhibitor` |
| `condition` | 疾病/状态 | `myocardial infarction` `diabetes mellitus` `community-acquired pneumonia` |
| `outcome` | 结局指标 | `mortality` `hospitalization` `hba1c` `egfr` |
| `study_type` | 研究类型 | `randomized controlled trial` `meta-analysis` `mendelian randomization` |

`\b` 的作用：`\bpirin\b` 不会匹配 `aspirin`，因为 `p` 前面是 `a`（同为词字符），边界不成立。

**缩写单独处理，且大小写敏感**：

```python
MEDICAL_ABBREVIATIONS = {"MI": "myocardial infarction", "DM": "diabetes mellitus", ...}
```

为什么不能用 `re.IGNORECASE` 一起匹配：小写 `mi`、`mr`、`bp` 在普通英文里大量出现（`mi` 是音符、`mr` 是先生）。只认全大写（或 `eGFR`/`HbA1c` 这类混合大小写）才能把误召回压到最低。这也是**歧义缩写被主动排除**的原因——`HR` 既是 heart rate 也是 hazard ratio，收录它必然出错，故不收。

中文走另一路：子串匹配 `ZH_TERM_MAP` 的 52 个键（中文没有词边界，正则 `\b` 对中文无效）。

## 5 查询版本生成

### 5.1 向量查询：只做缩写展开

`MI` → `myocardial infarction (MI)`，保留原形式作为线索。

**为什么不同义词一起拼进去**：缩写展开是纯增益（两者同义，不引入新语义），而把 `heart attack` `ami` `心肌梗死` 一起拼进查询会稀释语义重心，反而降低精度。同义词放到变体里供多路召回。

**替换必须一次性完成**。逐个 `re.sub` 会嵌套，这是个真实踩到的 bug：

```
逐个替换:  "死亡率" → "mortality (死亡率)"
           再替换 "死亡" → "mortality (mortality (死亡)率)"   ← 畸形
一次性替换: pat = re.compile("|".join(按长度降序的 surface))
           q = pat.sub(lambda m: f"{expansions[m.group(0)]} ({m.group(0)})", q)
```

### 5.2 关键词查询：为第二部分的 BM25 备好

输出空格分隔的词串。**中文查询必须输出英文关键词**——语料 99.4% 是英文，中文词做 BM25 几乎匹配不到任何东西。所以先映射到 canonical，再并入同义词，中文别名在此处被过滤掉。

### 5.3 变体

| 变体 | 内容 | 用途 |
|---|---|---|
| 0 | 主查询（缩写展开 / 中文原句） | 主力路 |
| 1 | 纯英文术语串（仅中/混查询） | 跨语言桥接路 |
| 2 | 同义词重述版本 | 换说法命中不同语义点 |

## 6 过滤条件提取

7 种时间表达，按"信息量从高到低"排列，只取最具体的一条：

| 模式 | 例 | 产出 |
|---|---|---|
| 区间 | `2020-2023` / `2020至2023` | `pub_year ∈ [2020..2023]` |
| 之后 | `2020年以后` / `since 2020` | `pub_year ∈ [2020..2026]` |
| 之前 | `2019年以前` / `before 2019` | `pub_year ∈ [1992..2019]` |
| 近 N 年 | `近五年` / `last 5 years` | `pub_year ∈ [2022..2026]` |
| 单年 | `2023` | `pub_year = 2023` |
| 表格 | `表格` / `table` | `is_table = True` |
| 语言 | `中文` / `chinese` | `lang = "zh"` |

### 6.1 为什么用 `$in` 枚举而不是 `$gte`

第一版写成 `{"pub_year": {"$gte": "2020"}}`，运行时直接报错：

```
ValueError: Expected operand value to be ...
```

根因：`pub_year` 在 Chroma 里存的是**字符串**（阶段③就是 `str`），而 Chroma 对字符串类型的元数据**不支持 `$gte`/`$lte` 比较**。改为显式枚举：

```python
def _year_list(y0, y1):
    return [str(y) for y in range(int(y0), int(y1) + 1)]
# → {"pub_year": {"$in": ["2020", "2021", ..., "2026"]}}
```

年份取值只有 35 个，展开成本可忽略，`$in` 对字符串完全可用。

## 7 三个靠实验纠正的判断

这一节是本次最有价值的部分：**任务书给的方法、以及我自己的第一版实现，都被实测数据推翻了**。

### 7.1 指令前缀：任务书说"加"，实测说"不加"

任务书写「准备向量检索查询：BGE 模型的最佳实践：添加指令前缀」。该结论出自 **bge v1.5 系列**的官方建议，而 bge-m3 训练时已内化检索指令。阶段④已做过对照（`docs/向量化与索引构建报告.md` §4）：

```
无指令: top1 sim 0.7422  ← 切题
加指令: top1 sim 0.6833  ← top1 被换掉，整体下降
```

本模块因此**默认关闭** `--instruction`，开关保留，换回 bge-base-en-v1.5 时可重开。

**方法论**：文档结论有适用边界，跨模型必须重测。记"为什么"而不是记"是什么"。

### 7.2 清洗去标点：有害

第一版 `clean_query()` 去掉了句尾标点，对照实验里立刻出现负例：

```
"Does metformin reduce cardiovascular mortality in type 2 diabetes?"
  原句(带 ?)  0.7422
  去标点      0.7273     ← 下降 0.0149
```

疑问标点携带"这是一个问句"的语义，是检索信号不是噪声。改为**只做全角转半角与空白压缩**。

### 7.3 中英桥接：拼接策略被消融实验否掉

语料 99.4% 是英文，中文查询怎么送进向量模型是真问题。三种候选各跑 4 条中文查询（`bench_query_enhancement.py --ablation`）：

| 查询 | A 原句 | B 原句+英文术语 | C 纯英文术语串 | 最优 |
|---|---|---|---|---|
| 二甲双胍对心血管疾病有何影响？ | 0.5953 | 0.6908 | **0.6943** | C |
| 抗生素治疗社区获得性肺炎的疗程 | **0.5509** | 0.4815 | 0.4990 | A |
| 近五年关于慢性肾病 eGFR | 0.6343 | 0.6810 | **0.7010** | C |
| MI 患者的死亡率 2020年以后 | 0.6513 | **0.7082** | 0.7032 | B |

B（拼接）在「抗生素」这条上比 A、C **都低约 0.05** —— 拼接稀释了语义，且这个稀释方向不可预测。

于是问：既然要多路召回，为什么不把 A 和 C 各做一路再取最优？计算 $\max(A, C)$ 与 B 的差：

| 查询 | $\max(A,C)$ | B | 差 |
|---|---|---|---|
| 二甲双胍 | 0.6943 | 0.6908 | +0.0035 |
| 抗生素 | 0.5509 | 0.4815 | **+0.0694** |
| 慢性肾病 | 0.7010 | 0.6810 | +0.0200 |
| MI 2020年以后 | 0.7032 | 0.7082 | −0.0050 |
| **平均** | | | **+0.0220** |

$\max(A,C)$ 在 4 条里 3 条优于 B，平均 +0.0220。**所以最终不拼接**：主查询保留中文原句，纯英文术语串作为独立变体，交给第二部分的多路召回融合——每次都能拿到两路里更好的那个，而不是赌单一策略。

补充一个反直觉观察：给「抗生素…肺炎」补词典（加入 `community-acquired pneumonia` / `CAP`）后，B 策略反而从 −0.0169 恶化到 −0.0694。**术语变多不等于检索变好**——这进一步说明拼接方向是错的，不是词典覆盖不够。

## 8 对照实验：增强到底有没有用

`baseline` = 原查询单路、无过滤；`enhanced` = 对所有变体逐路检索（都带过滤）取 top1 最高的一路，即下游多路召回融合后的实际效果。每条 `n=5`。

| 查询 | baseline | enhanced | $\Delta$ | 过滤合规 | 术语命中 |
|---|---|---|---|---|---|
| 二甲双胍对心血管疾病有何影响？ | 0.5953 | **0.6943** | +0.0990 | — | 1→1 |
| MI 患者的死亡率 2020年以后的研究 | 0.6513 | **0.7032** | +0.0519 | 80% → **100%** | 1→1 |
| Does metformin reduce cardiovascular mortality… | 0.7422 | **0.7499** | +0.0077 | — | 1→1 |
| SGLT2 inhibitor heart failure hospitalization | 0.6053 | **0.6122** | +0.0069 | — | 1→1 |
| 近五年关于慢性肾病 eGFR 的随机对照试验 | 0.6545 | **0.7010** | +0.0465 | 20% → **100%** | 1→1 |
| 抗生素治疗社区获得性肺炎的疗程 | 0.5509 | 0.5509 | +0.0000 | — | 1→1 |
| **平均** | **0.6332** | **0.6686** | **+0.0353** | | |

**结论**：6/6 无负例，平均 top1 +0.0353；两条带时间约束的查询过滤合规率从 80% / 20% 提升到 **100%**；中文查询获益最大（+0.0990 / +0.0519 / +0.0465）。

### 8.1 一个失效的指标，也记录下来

「术语命中」设计初衷是验证缩写展开是否把词带进了结果，实测 **baseline 6/6 → enhanced 6/6**，完全没有区分度。原因：查询里的医学词本身就会出现在相关文献中，baseline 用原词检索同样能命中——**这个指标测不出增强的增量**。它保留在脚本里，但不作为判据。

真正的判据只剩两个：top1 相似度、过滤合规率。

### 8.2 本次实验的局限（必须写明）

1. **样本仅 6 条**，且由我自己编写，存在"选了增强会赢的查询"的风险。
2. **top1 相似度不是相关性标注**。它只能证明"更靠近"，证明不了"确实相关"。要算 Recall@K / MRR，必须有 (问题, 相关块) 标注集——这是第二部分前最该补的东西。
3. 增强幅度在不同查询上差异极大（+0.0990 ~ +0.0000），说明**词典覆盖度决定收益**，而非增强机制本身。

## 9 环境与可复现性

运行前需启动 Ollama（`ollama serve`）。本次遇到并修复了一个环境级问题：

| 现象 | `ollama` Python 客户端全部报 `WinError 10061`，但同一时刻 `urllib` 直连 `11434` 正常 |
|---|---|
| 根因 | Windows 系统代理写在**注册表**里而非环境变量；`httpx` 默认 `trust_env=True` 会把 `localhost` 请求也发往代理 |
| 修复 | `embed_chunks.py` 顶部设置 `NO_PROXY = localhost,127.0.0.1,::1`，必须在创建 `ollama.Client` 之前 |
| 影响 | 不修的话换一台机器跑就会"莫名连不上"，且错误信息完全指向错误方向 |

## 10 产出与复现

```bash
# 单条查询的结构化结果
python scripts/query_understanding.py "MI 患者的死亡率 2020年以后的研究"

# JSON 输出（供下游调用）
python scripts/query_understanding.py "二甲双胍对心血管疾病有何影响？" --json

# 对照实验 / 中文桥接消融
python scripts/bench_query_enhancement.py

```

`EnhancedQuery` 字段：

| 字段 | 含义 | 下游用途 |
|---|---|---|
| `original` / `cleaned` | 原始 / 清洗后查询 | 日志与溯源 |

| `keyword_query` | 关键词检索入口 | 第二部分 BM25 |
| `filters` / `filter_notes` | 过滤条件 / 人类可读解释 | Chroma `where`、结果解释 |
